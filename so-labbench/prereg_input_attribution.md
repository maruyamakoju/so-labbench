# 事前登録: SmolVLA はカメラの代わりに何で動いているか

2026-09-14 登録 / **このファイルは測定を1本も走らせる前にコミットする。** git の時刻がその証拠である。
結果を見てからここを書き換えた場合は、書き換えた行と理由をこの文書の末尾に追記する。

## 背景

`finding_vision_reliance_act_vs_smolvla.md` で、全カメラを黒にしたときに方策の指令がどれだけ動くかを
8課題で測った。人手デモのばらつきに対して ACT は 82〜132%、SmolVLA は 9〜17%。

**SmolVLA の指令は、カメラをすべて失ってもほとんど変わらない。** では何で決まっているのか。
方策が受け取る入力は3種類しかない。

| 入力 | ACT | SmolVLA |
|---|---|---|
| 画像（前・上・手首） | 使う | 使う |
| 関節状態（6次元） | 使う | 使う |
| 指示文 | **使わない** | 使う |

同じ所見は「状態入力を摂動すれば問える」と書いて止まっている。ここで問う。

## 測り方

`rig_sensitivity.py` と同じ装置、同じ課題、同じ checkpoint、同じ種の固定。変えるのは摂動だけ。
**各入力の情報を1つずつ取り除き**、指令がどれだけ動くかを同じフレームで比べる。

| 摂動 | 何を取り除くか | 対象 |
|---|---|---|
| `all_blank` | 視覚（3台すべて黒） | 両方 |
| `state_mean` | 自己受容（関節状態を、その課題の標本フレームの平均で置き換える） | 両方 |
| `task_blank` | 言語（指示文を空文字列に） | SmolVLA |
| `task_other` | 言語（別の課題の指示文に置き換える。分布内の文だが課題が違う） | SmolVLA |
| `state_noise_0.5sd` | 関節状態に、関節ごとの標準偏差の0.5倍のガウス雑音 | 両方 |
| `state_noise_1sd` | 同、1倍 | 両方 |
| `state_gripper_1sd` | グリッパー関節の状態だけを標準偏差1つ分ずらす | 両方 |
| `resample` | 何も変えず種だけ変える（自己ノイズの床） | 両方 |
| `identity` | 何も変えない（**必ず 0**。0 でなければ配線が壊れている） | 両方 |

- 状態の標準偏差は、その課題で標本にした**フレームの状態そのもの**から関節ごとに計算し、CSV に記録する。
- 状態の雑音は、フレーム番号で種を固定した乱数で作る。再実行で同じ値になる。
- **stride 50**（全課題）。比較はすべて同じ実行・同じフレームの中で行うので、グリッド（stride 25）と
  標本数が違っても比較は崩れない。SmolVLA 約3時間、ACT 約20分の見込み。
- 8課題すべて。`tasks.json` の順。

### 比較の非対称について、先に書いておく

黒い画像は学習分布から大きく外れるが、平均の関節状態は分布の中にある。**この非対称は視覚を
重要に見せる方向に働く。** したがって、もし `state_mean` が `all_blank` より大きく動かすなら、それは
不利な比較を覆しての結果であり、控えめな結論になる。逆方向（視覚が勝つ）は、この非対称で
一部説明できてしまうので、強くは読まない。

## 仮説と判定規則

判定はすべて**8課題中7課題以上**（片側符号検定 p = 0.035）。6課題以下は「支持されない」と書く。
中間の言い方はしない。

**H1（主）SmolVLA は視覚より自己受容に頼る。**
SmolVLA で、`state_mean` による指令の動きが `all_blank` によるものより大きい課題が 8課題中7以上。

**H2（主）SmolVLA は指示文をほとんど使わない。**
SmolVLA で、`task_blank` と `task_other` の**両方**が、自己ノイズ（`resample`）の2倍未満にとどまる課題が
8課題中7以上。
根拠: 各 checkpoint は1つの課題だけで、**毎回同じ指示文**を与えて微調整されている。微調整の間、
指示文は情報を1ビットも運ばないので、使わないことを学ぶはずである。

**H3（対照）ACT は自己受容より視覚に頼る。**
ACT で、`all_blank` による動きが `state_mean` によるものより大きい課題が 8課題中7以上。

**H4（装置の検算）状態の摂動が効いている。**
両方策で、`state_noise_1sd` の動きが `state_noise_0.5sd` より大きい課題が、それぞれ 8課題中7以上。
**これが成り立たなければ、状態の摂動が壊れているので H1 と H3 は解釈しない。**

**有効性の条件**: `identity` が両方策・全課題で厳密に 0。1つでも 0 でなければ、その実行は無効として
結果を書かず、原因を直してやり直す。

## 分母

H1・H3 は同じ方策・同じ課題の中で2つの摂動を比べるので、分母を何にしても判定は変わらない。
それでも表は生の値・自然変動比・行動のばらつき比の3つで出す（`vision_reliance.py` と同じ規則）。
H2 は自己ノイズとの比なので、これも方策内で閉じている。

## 結果の読み方を先に決めておく

| 結果 | 読み |
|---|---|
| H1 成立 | SmolVLA の指令は主に関節状態で決まっている。昨日の所見の「なぜ動かないか」の答えになる |
| H1 不成立、`state_mean` も小さい | SmolVLA はどの入力にも鈍い。指令は入力よりも、行動チャンクや事前分布で決まっている |
| H1 不成立、`all_blank` のほうが大きい | 視覚が勝つが、上の非対称で一部説明できるので、強くは言わない |
| H2 成立 | 課題ごとの微調整で、言語条件付けは実質的に使われていない |
| H2 不成立 | 一定の指示文で微調整しても、指示文は指令を動かす。それ自体が所見になる |
| H3 不成立 | ACT も自己受容に頼っている。H1 の結果を SmolVLA 固有と言えなくなる |

## 言えないこと（先に決めておく）

- **「使っている」の意味は、取り除いたときに指令が動くことに限る。** 入力を読んで指令をほとんど
  変えない方策と、その入力を無視する方策は、ここでは区別できない。
- 教師強制の単ステップ予測であって、閉ループのロールアウトではない。
- 方策は2つ、VLA は1つ。VLA 一般については何も言わない。
- 各 checkpoint は課題ごとの微調整で、アーキテクチャと学習手順は分けられない。

## 追記欄（結果を見た後の変更はここに書く）

**2026-09-14 追記1（測定前、実装時）**: 仮説は変えていない。検算を1つ足した。

ACT は指示文を入力に取らないので、`task_blank` と `task_other` を ACT にもかけ、**指令の動きが厳密に
0 になること**を2つ目の配線検算とする。0 でなければ、指示文以外の何かが摂動と一緒に変わっている。
仮説の判定には使わない。

実装は `armnetbench/input_attribution.py`、判定規則は `armnetbench/judge_input_attribution.py`。
判定規則は合成データ49項目で検算し（`test_input_attribution.py`）、閾値を6に落とす・同点を勝ちに
数える・H3をH1と同じ向きで判定する・H4の門を外す、など16通りに壊して全部検出することを
確認してから走らせる（`mutation_check.py`、全体で43通り）。

走らせる前に、1エピソードだけの試運転で `identity` が 0 になることを確かめる。試運転の数値は
配線の確認にだけ使い、仮説の判定には使わない。

**2026-09-14 追記2（本番の前、ただし試運転と配線検査の結果を見た後）**:
**判定規則・閾値・仮説はどれも変えない。** 見たもの、見つけた欠陥、それをどう報告するかだけを書く。

*見たもの*（どちらも判定には使わない）:
- 試運転（eye_drops_to_basket、1エピソード5フレーム）: `identity` は両方策で 0、ACT の
  `task_blank`/`task_other` も 0。配線は合格。
- 配線検査（同課題の1フレーム）: 全関節を +100 ずらすと、モデルに入る**正規化済みの状態は
  約1から約6に変わる**のに、ACT の指令は 0.094 しか動かない。SmolVLA は +10 で 7.9 動く。
  状態は両方策に同じ値・同じ正規化で届いており、ACT は実質的に関節状態を使っていない。

*見つけた欠陥*: **H4 は「装置が壊れている」と「方策がその入力を無視している」を区別できない。**
H4 の目的は前者の検出だったが、ACT のように本当に状態を無視する方策では、倍の雑音でも指令が
ほとんど動かず、数値誤差の大小で H4 が落ちうる。そうなると登録規則により H1 と H3 が
「解釈しない」になり、**最も情報のある結果が、装置の故障と同じ扱いで伏せられる。**

*どう報告するか*:
1. H1〜H4 の判定は**登録どおりに**出し、そのまま書く。H4 が落ちて H1・H3 が「解釈しない」に
   なっても、その判定を書き換えない。
2. それとは別に、**事後の観察と明記して**、状態がモデルの入力まで届いていることを示す配線検査を
   載せる（正規化後の状態の変化量）。これは判定ではなく、H4 の欠陥を読者が評価するための材料である。
3. 次に同じ種類の事前登録を書くときは、装置の検算を方策の応答から切り離す（入力テンソルが
   変わったことを直接確かめる）。

*もう1つ確かめたこと*: SmolVLA の画像入力名は `camera1/2/3` で、我々は `front/top/wrist` で
渡している。前処理が `top→camera1, wrist→camera2, front→camera3` と付け替えており、この対応表は
**8つの checkpoint すべてで同一、かつ各 `train_config.json` と一致**した。学習時と同じ枠に画像が
入っている。したがって `finding_vision_reliance_act_vs_smolvla.md`（公開済み）の結果は配線の
産物ではない。
