# 所見（否定的）: 「人間より掴み直す方策は失敗する」は、8課題に広げると消える

2026-09-14 / 公開データのみ、実機も GPU も不要 / `armnetbench/retry_rate.py`
検算: `armnetbench/test_retry_rate.py`（24項目、合成データで既知解と照合）
出力: `retry_rate_episodes.csv`（2,499本）/ `retry_rate_cells.csv`（56セル）/ `retry_rate_within_cell.csv`

## 何を確かめたかったか

`finding_failure_anatomy.md` で、7方策すべてが 0.000 の `cable_clip` について、
**方策は人手デモの3回に対し5〜17.5回も掴み直している**ことを示した。再試行そのものは
正しく実行されているのに、1回を成功させる何かが足りない、と書いた。

**しかし根拠は1課題である。**対照を入れても2課題で、それは逸話であって法則ではない。
ベンチマークは8課題×7方策の行動軌跡を全部公開しているので、**56セルで一度に問える。**
「人間より頻繁に掴み直す方策は、成功率が低いか？」

## 罠を先に書く

v0.1 は課題ごとの制限時間を設けておらず、**操作者が手で止めていた**。だから失敗した試行は
成功した試行より長い。試行あたりで数えた量は、閉じ回数を含めて全部この長さを引き継ぐ。
「失敗は掴み直しが多い」は「失敗は長い」の言い換えになりうる。

対策を2つ置いた。

1. **主指標は1秒あたりの閉じ回数**。長さは割り算で消える。
2. **本命の検定はセル内**。同じ方策・同じ課題で、成功した試行と失敗した試行を比べる。
   課題の難しさも方策の素性も操作者の癖も、セル内では固定される。

閾値も決め打ちしない。ベンチマークの行動値は録画したアームの較正レンジに対する割合なので
（`finding_calibration_portability.md`）、15 や 40 という数字を持ち込むのは**別のアームの定数を
輸入すること**である。各課題の人手デモのグリッパー分布は二山になるので、その2つの山を最もよく
分ける切れ目（Otsu）を課題ごとに測った。結果は 8.1 から 17.7 まで課題ごとに違った。

## 結果1: 課題をまたいだ相関は、正規化の仕方だけで符号が変わる

56セルで、閉じ頻度と成功率の相関:

| 測り方 | 相関 | 95%区間 | |
|---|---|---|---|
| 1秒あたりの閉じ回数（生） | **+0.34** | +0.09 .. +0.56 | ゼロを除外 |
| 同、人手デモの何倍か | **−0.38** | −0.58 .. −0.12 | ゼロを除外 |
| 試行あたりの閉じ回数（人手比） | −0.63 | −0.76 .. −0.43 | 長さに汚染 |
| 試行の長さ（秒） | −0.66 | −0.79 .. −0.49 | |

**同じデータ、同じ56セルで、符号が逆の「有意な」相関が2つ出る。** どちらも正当化できる
正規化である。片方だけ選んで止めていたら、選んだ側の符号で自信のある結論を書いていた。

理由は測れる。**人手デモ自身の閉じ頻度が、その課題の平均成功率と r=+0.89 [+0.50 .. +0.98]
（n=8課題）で相関している。** つまり人間の閉じ頻度は「その課題の易しさ」の代理変数である。
それで割れば易しさが消え、符号は機械的に反転する。**課題をまたいだ相関は、どちらも
掴み直しについての証拠ではない。課題の難易度を測っているだけである。**

## 結果2: セル内の検定は、何も出ない

成功3本・失敗3本以上を持つ43セルで、失敗試行の閉じ頻度から成功試行の閉じ頻度を引く。

| | |
|---|---|
| 失敗のほうが多かったセル | **24 / 43** |
| 符号検定（片側） | **p = 0.271** |
| 差の中央値 | **+0.007 回/秒** |

**コイン投げと区別がつかない。** 差の中央値 0.007 回/秒は、40秒の試行で 0.3 回である。

## 結果3: 閾値を動かすと、その「何も出ない」すら安定しない

閾値を ±33%、最短閉じ時間を2〜5フレームで振った9通り:

| | 生の相関 | 人手比の相関 | セル内符号検定 |
|---|---|---|---|
| 閾値×0.75, 最短2 | +0.25 | −0.40 | 28/43 **p=0.033** |
| 閾値×0.75, 最短5 | +0.35 | −0.34 | 21/43 p=0.620 |
| 実測値, 最短3（主指標） | +0.34 | −0.37 | 24/43 p=0.271 |
| 閾値×1.33, 最短2 | +0.40 | −0.23 | 24/43 p=0.271 |
| 閾値×1.33, 最短5 | **+0.46** | −0.18 | **17/43 p=0.937** |

生の相関は +0.25〜+0.46、人手比は −0.40〜−0.18、セル内検定は p=0.033 から p=0.937 まで動く。
**「閾値を 25% 動かす」も「掴みの最短時間を 0.1 秒から 0.25 秒にする」も、どちらも
誰も止めない選択である。** それだけで有意にも無意味にもなる。

## 結果4: 最初の1課題を抜くと、残った相関も消える

| | 相関 | 95%区間 |
|---|---|---|
| 8課題すべて | −0.38 | −0.58 .. −0.12 |
| **`cable_clip` を除く** | **−0.22** | **−0.47 .. +0.07** |
| `eye_drops_to_basket` を除く | −0.41 | −0.62 .. −0.14 |
| `tool_insert` を除く | −0.38 | −0.60 .. −0.11 |

**仮説の出どころである課題を抜くと、区間がゼロを跨ぐ。** 他の課題を抜いても動かないので、
これは一般的な脆さではなく、**種にした1課題が相関を担いでいた**ということである。

## 結論

**「人間より掴み直す方策は失敗する」は、このベンチマークでは支持されない。**
セル内の検定は無、課題をまたいだ相関は正規化で符号が変わり、閾値の細部で有意性が動き、
残った分も出発点の1課題が担いでいる。4つのうちどれか1つでも十分に否定的である。

**ただし `cable_clip` の観察そのものは残る。**

| 課題 | 人手比の閉じ頻度 | 平均成功率 |
|---|---|---|
| **cable_clip** | **1.63倍** | **0.00** |
| tool_removal | 1.36 | 0.22 |
| tool_insert | 1.27 | 0.22 |
| block_stack | 1.24 | 0.16 |
| ring_insert | 1.21 | 0.35 |
| eye_drops_to_shelf | 1.15 | 0.34 |
| cable_unclip | 1.15 | 0.40 |
| eye_drops_to_basket | 1.13 | 0.52 |

`cable_clip` は8課題で最も掴み直す課題であり、唯一全方策が 0.000 の課題である。
**それは事実だが、法則の実例ではない。**「掴み直しの多さ」を方策や課題の
健全性指標として使うことはできない。

## 方法についての注記——これが本当の所見かもしれない

このデータには、**正当化できる解析上の選択が3つ**ある。生の頻度か人手比か。閾値をどこに引くか。
何フレームから掴みと呼ぶか。その組み合わせで、相関は **+0.46 から −0.40** まで動き、
その多くが「ゼロを除外」する。

私は最初、人手比・実測閾値・最短3フレームだけを計算した。r=−0.38、区間はゼロを除外。
**そこで止めていれば、8課題に一般化した確信のある所見を書いていた。** 止めなかったのは、
感度検査が主指標と別の量を測っているバグに気づいたからで、ほとんど偶然である。

**ArmnetBench を使う人へ**: 行動軌跡から導く指標は、閾値と正規化を両方公開してほしい。
そして課題をまたいだ相関を出す前に、その量が課題の難易度と相関していないか確かめてほしい。
人手デモの閉じ頻度は難易度と r=+0.89 だった。同じ罠は他の量にもある。
